# 队列矩阵里 0 个缺失：这才是联合基因型该有的样子

（编号 023 · 实测：1000G Phase3 chr22 / 2504 样本 × 5431 位点；GATK 与 GLnexus 未安装）

**要点一｜缺失基因型的数量，能一眼看出是不是联合基因型**
实测本数据：

```
样本数 = 2504 ；缺失基因型总数 = 0 ；每样本均值 = 0.00
```

**2504 个样本、5431 个位点上没有任何一个 `./.`**。这就是联合基因型「平方化」的产物特征——每个变异位点上每个样本都由**证据**填满（`0/0` 或携带型）。

对照一下：如果用 `bcftools merge` 合并单样本 VCF，某样本「没这个位点」会用 `./.` 填充而**不是** `0/0`。于是「真的纯合参考」和「压根没评估过」变得不可区分，下游等位频率和关联检验全错。所以**永远不要拿 merge 当联合基因型**。

**要点二｜gVCF 的 `<NON_REF>` 是这一切的前提**
`-ERC GVCF` 在每个位置（包括非变异位置）都记录「该位点为纯合参考」的置信度，并且每条记录带一个符号等位 `<NON_REF>`（「任何尚未观测到的等位」），针对它算 AD/PL。

两个后果：① **前向兼容**——某个变异在本样本看起来是参考也没关系，等别的样本发现它，还能用 `<NON_REF>` 的证据在本样本里重新评估；② **能区分「确证纯合参考」与「没数据」**，这正是平方化的来源。另外昂贵的组装只做一次，加第 N+1 个样本时只需重跑廉价的合并与基因分型。

顺带：联合基因分型会**重算** GQ 和 PL（针对最终确定的队列等位集合），所以某样本在联合 VCF 里的基因型可能与它自己的 gVCF 暗示的不同——那是「低覆盖位点被队列证据救援」在起作用，不是 bug。

**要点三｜GATK 与 GLnexus 怎么选，以及 GenomicsDB 的内存地雷**
- 队列 < 100：CombineGVCFs 就够；100–10,000：GenomicsDB + GenotypeGVCFs，按染色体分片；> 100,000：DeepVariant + GLnexus 或 Hail VDS。
- GenomicsDB 有个反直觉的坑：**重活在原生 C/C++（TileDB）里，所以 JVM 堆要限制在内存的 80–90%**，给多了会让原生层缺内存，报出一个看起来跟堆无关的 OOM。
- GenomicsDB **没有样本替换**：只能加不同名的新样本，改一个样本就得重建工作区；区间在导入时锁定，增量更新扩不了区间。增量添加前一定备份。

参考吞吐（Yun 等，2504 样本 chr22）：GLnexus 合并 0.84 h vs GATK 6.83 h；DeepVariant gVCF 占用 2.20 TB vs GATK 15.16 TB。

**结论**：队列矩阵的每个单元格都该由证据填充，而不是由假设填充。拿到 callset 先数一眼缺失基因型，就能判断它到底是不是联合基因型的产物。

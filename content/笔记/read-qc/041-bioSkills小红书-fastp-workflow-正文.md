# 一条命令做完六道工序：fastp 真机实测

META
标题建议: fastp一次跑完，六道工序各干多少活
封面卡: 60,000 条读 → 50,612 条｜Q30 52.96% → 62.10%｜用时 1 秒
/META

（编号 041 · 真跑日期 2026-09-03：WSL Ubuntu + fastp 1.3.6；模拟 PE 数据 60,000 条读 × 100 bp，内置接头、低质量、多 N、超短 insert 四类缺陷）

**要点一｜接头序列不用给，overlap 分析自己找**
模拟数据里 24.3% 的读带 read-through 接头，一条接头序列都没指定，fastp 靠 R1 与 R2 的反向互补重叠分析定位 insert 边界，裁掉 12,739 条读上的 451,574 个碱基。同一套重叠分析还顺带做碱基校正：重叠区一侧质量高、一侧质量低的错配，用高质量的覆盖低质量的，本次修正 5,891 条读里的 9,688 个碱基。序列匹配类工具最少要 3 个碱基才能认出接头，overlap 法裁到只剩 1 个碱基也能定位。

**要点二｜滑窗剪裁会抢过滤器的活，过滤计数为零要会读**
数据里故意埋了 6,592 条低质量读和 1,506 条多 N 读。开启 `--cut_right` 滑窗剪裁的全流程下，`low_quality_reads` 与 `too_many_N_reads` 计数都是 0——低质量尾巴和多 N 区段先被剪掉，逐条过滤器拿不到可判失败的读。关掉剪裁的对照组里，两个计数才分别变成 6,592 和 1,506。保留读数同样是对比信号：全流程保留 50,612 条，关剪裁组保留 50,076 条，剪裁救回的比过滤器丢弃的多 536 条。报告里过滤计数为 0，可能是数据干净，也可能是上游工序代劳了。

**要点三｜Q30 率 52.96% → 62.10%，各工序的贡献可以拆开算**
全流程保留 84.4% 的读，Q30 率提升 9.15 个百分点。三组消融实测各工序贡献：关掉接头去除，Q30 降到 59.83%（差 2.28 个百分点）——接头集中在 3' 端、质量偏低，留在读里拖低整体质量分布；关掉长度过滤，保留 59,998 条读但 R1 平均读长掉到 82 bp，9,388 条超短读全部混了进来。

**结论**：一条命令完成接头去除、质量剪裁、逐条过滤、碱基校正、QC 报告，60,000 条读用时 1 秒，bulk PE 预处理默认选手的地位名副其实。使用侧记住两件事：`low_quality_reads = 0` 未必等于数据干净；`--dedup` 是序列一致性去重，表达量与扩增子数据别用。
